# План рефакторинга серверной части: Переход к Модульному Монолиту

Данный документ описывает детальный, поэтапный план архитектурного рефакторинга серверной части проекта на основе результатов ревью. 

**Целевая архитектура:** Модульный монолит с использованием принципов Clean Architecture и Ports and Adapters.

---

## Этап 1: Устранение критических рисков (Stage-0)
*Цель: Обеспечить безопасность приложения, стабильность данных и предсказуемость фоновых задач.*

### 1.1 Безопасность и управление секретами
*   **Проблема:** HTTP API позволяет изменять локальный файл `.env` с секретами.
*   **Действие:** 
    *   Удалить функции `_update_env_file`, эндпоинты `save_tokens`, `clear_tokens` из `services/bot/main.py`.
    *   Оставить работу с `.env` строго в режиме чтения при инициализации приложения.

### 1.2 Правильные фоновые задачи (Отказ от CLI subprocess)
*   **Проблема:** API запускает обновление RAG как дочерний CLI-процесс (`subprocess`), что лишает приложение контроля над выполнением, статусами и изоляцией ошибок.
*   **Действие:**
    *   Создать слой сервисов сценариев (Application Services).
    *   Реализовать `UpdateRagService`, инкапсулирующий логику обновления.
    *   Заменить запуск CLI-команды в `/api/update-rag` на фоновое выполнение `UpdateRagService` средствами Python (с сохранением статуса задачи).

### 1.3 Согласованность данных (SQLite + JSONL)
*   **Проблема:** Отсутствие единой границы транзакции. Сбой может привести к рассинхронизации метаданных в БД и векторного хранилища.
*   **Действие:**
    *   Внедрить паттерн `UnitOfWork` для синхронной фиксации изменений.
    *   Изменить `JsonVectorStore`: реализовать атомарный *upsert* (вставка/обновление) по `document_id` и `content_hash`, чтобы исключить полное переписывание `documents.jsonl` при локальных изменениях.

### 1.4 Оптимизация обхода Confluence
*   **Проблема:** Инкрементальное обновление начинается с полного рекурсивного обхода всех страниц.
*   **Действие:**
    *   Реализовать "ConfluenceCatalogRepository" / `PageSnapshotValidator`.
    *   Сверять локальный снимок (`PageSnapshotRepository`) с датами `lastModified` на сервере перед запуском глубокого парсинга вложений.

## Этап 2: Чистая архитектура и декомпозиция (Stage-1)
*Цель: Разгрузить перегруженные модули, выделить слои и подготовить базу для легкого развития.*

### 2.1 Декомпозиция слоя API (`services/bot/main.py`)
*   **Проблема:** Файл перегружен (эндпоинты, настройки, CLI, SQL, фильтрация).
*   **Действие:**
    *   Разделить `main.py` на FastAPI роутеры (например, `api/routers/chat.py`, `api/routers/sync.py`, `api/routers/system.py`).
    *   Вынести бизнес-логику и SQL-запросы в сервисы (например, `ChatHistoryService`, `SyncStatusService`).

### 2.2 Рефакторинг RAG Retriever (`services/rag/retriever.py`)
*   **Проблема:** Один класс отвечает за классификацию интентов, поиск данных, формирование структурированных ответов и резервный векторный поиск.
*   **Действие:**
    *   Реализовать паттерн "Диспетчер" (`IntentDispatcher`).
    *   Разнести логику по обработчикам: `StructuredAnswerHandler`, `VectorAnswerHandler`, `ReleaseChangesHandler`.

### 2.3 Декомпозиция Confluence Parser (`services/ingestion/confluence/parser.py`)
*   **Проблема:** Парсер выполняет множество специализированных задач извлечения фактов и чек-листов, подавляя ошибки через `except Exception: pass`.
*   **Действие:**
    *   Разделить на классы: `FactExtractor`, `ChecklistExtractor`, `S2TSelector`.
    *   Заменить `pass` на явное логирование или генерацию доменных событий.

### 2.4 Наблюдаемость и аудит
*   **Проблема:** Нет единой модели событий; ошибки логируются, но недоступны для контроля статуса синхронизации.
*   **Действие:**
    *   Внедрить `EventRecorder` (уровни: info, warn, alert).
    *   Записывать доменные события (например, отсутствие доступа к витрине) в базу для последующего анализа.

### 2.5 Актуализация документации
*   **Действие:** Обновить `docs/architecture.md`, `docs/project_map.md` и `docs/README.md`, четко разделив текущее состояние (Модульный монолит) и возможное целевое (Микросервисы).

## Этап 3: Эксплуатационная надежность (Stage-2)
*Цель: Обеспечить стабильность в промышленной среде.*

### 3.1 Версионирование базы данных
*   **Проблема:** Схема БД развивается "на лету" через ручные проверки колонок.
*   **Действие:** Внедрить инструмент миграций (например, Alembic) для предсказуемого наката структуры SQLite.

### 3.2 Тестирование
*   **Действие:** Написать/дополнить тесты для новых FastAPI роутеров, фоновых задач и логики согласованного *upsert* в векторном хранилище.

## Целевой поток выполнения

**Оркестрация загрузки (UpdateRagService):**
```text
UpdateRagService
  -> ConfluenceSyncOrchestrator
    -> CatalogDiffDiscovery (поиск изменений)
    -> ConfluenceExtractors (парсинг)
    -> S2TDownloadPolicy
    -> S2TParser
    -> AttributeDiffService
    -> RAGIndexUpsertService (Unit of Work)
    -> SyncStateRepository
    -> EventRecorder
```

**Ответ на вопрос (AskQuestionService):**
```text
AskQuestionService
  -> IntentDispatcher
    -> StructuredAnswerHandler (или VectorAnswerHandler)
    -> LLMAnswerGenerator
    -> ResponseFormatter
```
