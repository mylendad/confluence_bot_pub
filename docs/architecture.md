# Архитектура проекта

## Текущее состояние: Модульный Монолит
Проект реализован как **Модульный Монолит** с применением принципов Clean Architecture и Ports & Adapters.
Это позволяет обеспечить высокую скорость разработки и простоту эксплуатации, сохраняя при этом строгие доменные границы для возможного будущего выделения микросервисов.

### Основные слои (Clean Architecture)
1. **Точки входа (Адаптеры управления):**
   - `services/bot/main.py`: FastAPI приложение с выделенными маршрутизаторами (`api/routers/`).
   - `services/bot/cli.py`: Typer CLI для управления процессами из командной строки.
2. **Слой сценариев (Application Services):**
   - Оркестрирует бизнес-задачи (`services/scenarios/`), такие как `UpdateRagService`, `ChatHistoryService`, `SyncStatusService`. Отделяет HTTP/CLI контроллеры от бизнес-логики.
3. **Доменный слой (Domain & Dispatchers):**
   - Разделен на изолированные модули: парсинг Confluence (`services/ingestion/confluence/extractors/`), парсинг Excel/CSV (`services/ingestion/s2t/`), поиск изменений (`services/ingestion/changes/`).
   - `services/rag/`: Содержит диспетчер намерений (`IntentDispatcher`) и специализированные обработчики RAG-запросов (Handlers).
4. **Слой хранения (Data Adapters):**
   - `shared/storage/`: Реализует репозитории поверх SQLite с поддержкой локальных транзакций (UnitOfWork).
   - Векторное хранилище (`JsonVectorStore`) реализует атомарный upsert без использования полноценной векторной СУБД.

### Ключевые механизмы
*   **Инкрементальная синхронизация:** Вместо полного сканирования Confluence используется сверка снимков (`PageSnapshotRepository`), что минимизирует количество API-вызовов и повторных загрузок файлов.
*   **Согласованность данных:** Запись в базу SQLite (метаданные, история, состояние) и векторное хранилище (JSONL) объединена контекстным менеджером SQLite транзакции, гарантирующим атомарность обновления.
*   **Управление секретами:** Секреты загружаются исключительно из окружения (`.env`) при старте приложения; локальное изменение секретов через REST API строго запрещено.

## Целевое состояние (Будущее развитие)
При росте нагрузки, увеличении объема корпуса документов (более 10-20 тысяч) или масштабировании команды разработки, проект подготовлен к переходу на микросервисную архитектуру:
1. Выделение фоновых задач синхронизации в отдельный Worker (с использованием очередей RabbitMQ или Redis).
2. Замена локального `JsonVectorStore` на специализированное промышленное решение с сохраняемыми эмбеддингами (pgvector / Chroma / FAISS).
3. Переход от автоматического управления схемой SQLite (schema diff) к предсказуемым, версионированным миграциям баз данных (Alembic).
